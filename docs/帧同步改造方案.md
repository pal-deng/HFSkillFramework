## 1. 帧同步核心要求

帧同步要求：**相同输入 + 相同初始状态 + 相同逻辑 = 相同结果**。  
为此必须满足：

1. **确定性运算**：禁止浮点数，使用定点数（FixedPoint）
2. **确定性物理**：禁止 Unity 引擎物理，使用确定性空间查询
3. **确定性时间**：禁止 `Time.deltaTime` / `Time.time`，使用固定逻辑帧步长
4. **确定性驱动**：禁止 `MonoBehaviour.Update`，由逻辑帧调度器统一 Tick
5. **表现与逻辑分离**：逻辑层只做数值和状态计算，表现层（特效/动画/位移渲染）在渲染帧同步表现

## 2. 阻断性问题（必须改造）

### 2.1 浮点数运算 → 定点数

**原因**：IEEE 754 浮点数在不同 CPU 架构、编译器优化级别下存在精度差异，相同的浮点运算可能产生不同的最低位结果，帧同步中会累积为不同步。

**涉及文件与代码**：

| 文件 | 问题代码 | 说明 |
|------|---------|------|
| `Runtime/Effect/DamageEffectSpec.cs` | `float baseDamage = CalculateDamage(...)` | 伤害计算全程 float |
| `Runtime/Effect/DamageEffectSpec.cs` | `baseDamage *= 100f / (100f + defense.Value)` | 除法运算精度不确定 |
| `Runtime/Effect/GameplayEffectSpec.cs` | `public float Duration`、`public float Period` | 效果持续时间/周期 |
| `Runtime/Effect/GameplayEffectSpec.cs` | `ElapsedTime += deltaTime` | 累加浮点时间 |
| `Runtime/Utils/GASTimer.cs` | `ElapsedTime += deltaTime` | 计时器累加 |
| `Runtime/Utils/GASTimer.cs` | `Progress => Duration > 0 ? ElapsedTime / Duration : 1f` | 进度计算 |
| `Runtime/Effect/DisplaceEffectSpec.cs` | `float moveStep = nodeData.speed * deltaTime` | 位移步长 |
| `Runtime/Effect/DisplaceEffectSpec.cs` | `float distToCaster = Vector3.Distance(...)` | 距离计算 |
| `Runtime/Effect/ProjectileEffectSpec.cs` | `Vector2 direction = (targetPosition - launchPosition).normalized` | 方向归一化 |
| `Runtime/Target/TargetSearcher.cs` | `float angleToTarget = Vector3.Angle(forward, dirToTarget)` | 角度计算 |
| `Runtime/Ability/GameplayAbilitySpec.cs` | `_currentPlayTime += deltaTime` | 动画播放时间 |
| `Runtime/Core/AbilitySystemComponent.cs` | `Tick(float deltaTime)` | 整个 Tick 链使用 float |

**改造方案**：

- 引入定点数库（如 `Fix64`，内部用 `long` 存储，支持加减乘除和基本数学函数）
- 将所有 `float` 替换为 `Fix64`
- 将 `Vector2` / `Vector3` 替换为 `FixVector2` / `FixVector3`
- `Mathf` 相关函数替换为定点数版本（`Sin`、`Cos`、`Sqrt`、`Atan2` 等）
- 注意：`Mathf.Atan2` 在 `ProjectileController.UpdateRotation()` 中用于朝向，需要定点数实现

**影响范围**：框架 Runtime 层全部文件，是改造量最大的部分。

---

### 2.2 Unity Physics → 确定性空间查询

**原因**：Unity `Physics` / `Physics2D` 的碰撞检测底层依赖 PhysX / Box2D，这些物理引擎不保证跨平台确定性。不同客户端搜索到的目标列表可能不同，导致技能效果不同步。

**涉及文件与代码**：

| 文件 | 问题代码 | 说明 |
|------|---------|------|
| `Runtime/Target/TargetSearcher.cs` | `Physics.OverlapSphere(center, radius, layerMask)` | 圆形范围搜索 |
| `Runtime/Target/TargetSearcher.cs` | `Physics.OverlapBox(center, halfExtents, orientation, layerMask)` | 矩形范围搜索 |
| `Runtime/Target/TargetSearcher.cs` | `Physics.Raycast(origin, direction, ..., maxDistance, layerMask)` | 射线搜索 |
| `Runtime/Target/TargetSearcher.cs` | `Physics.RaycastAll(origin, direction, maxDistance, layerMask)` | 射线搜索（全部） |
| `Runtime/Effect/ProjectileController.cs` | `Physics2D.OverlapCircleAll(_currentPosition, _data.CollisionRadius)` | 投射物碰撞检测 |

**改造方案**：

- 建立确定性的空间分区结构（四叉树或均匀网格），由逻辑层维护所有单位的逻辑位置
- 在 `TargetSearcher` 中改为遍历空间分区结构做范围查询，使用定点数距离/角度判断
- `ProjectileController` 的碰撞检测同样改为遍历空间分区结构，用定点距离判断碰撞
- 注意排序问题：搜索结果的遍历顺序也必须确定性（按单位ID排序，而非物理引擎返回顺序）

**影响范围**：`TargetSearcher`、`ProjectileController`，以及需要新增空间分区管理系统。

---

### 2.3 引擎时间 → 逻辑帧时间

**原因**：`Time.deltaTime` 是引擎渲染帧间隔，不同设备帧率不同导致每帧步长不同；`Time.time` 从引擎启动开始累积，不同客户端可能不同。帧同步要求所有客户端使用相同的固定逻辑帧步长。

**涉及文件与代码**：

| 文件 | 问题代码 | 说明 |
|------|---------|------|
| `Runtime/Ability/GameplayAbilitySpec.cs` | `ActivationTime = UnityEngine.Time.time` | 技能激活时间记录 |
| `Runtime/Effect/GameplayEffectSpec.cs` | `ActivationTime = UnityEngine.Time.time` | 效果激活时间记录 |
| `Runtime/Effect/GameplayEffectSpec.cs` | `ElapsedTime += deltaTime` | deltaTime 来源最终是 `Time.deltaTime` |
| `Runtime/Effect/ProjectileController.cs` | `float deltaTime = Time.deltaTime` | 投射物 Update 中直接读取 |
| `Runtime/Core/AbilitySystemComponent.cs` | `Tick(float deltaTime)` | deltaTime 由外部传入，但调用方可能使用 `Time.deltaTime` |

**改造方案**：

- 定义全局逻辑帧调度器（`LockstepScheduler`），以固定帧率（如 30fps）驱动 Tick
- `deltaTime` 统一使用固定步长常量（如 `1/30`，用定点数表示）
- 移除所有 `Time.time` 引用，改为维护一个全局逻辑帧计数器（`LogicFrame`）
- `ActivationTime` 改为记录 `LogicFrame`

**影响范围**：需要在 `AbilitySystemComponent.Tick` 的调用方（如 `Unit.cs` 或新的调度器）中替换时间源，以及 `ProjectileController` 中移除 `Time.deltaTime`。

---

### 2.4 MonoBehaviour.Update → 逻辑帧驱动

**原因**：`MonoBehaviour.Update` 由引擎渲染帧驱动，不同设备帧率不同。帧同步要求所有逻辑由统一的逻辑帧调度器驱动。

**涉及文件与代码**：

| 文件 | 问题代码 | 说明 |
|------|---------|------|
| `Runtime/Effect/ProjectileController.cs` | `private void Update()` | 继承 `MonoBehaviour`，在 `Update` 中驱动飞行和碰撞 |
| `Runtime/Effect/ProjectileController.cs` | `float deltaTime = Time.deltaTime` | Update 内读取引擎时间 |

**改造方案**：

- `ProjectileController` 改为纯 C# 类（`public class ProjectileController`），不继承 `MonoBehaviour`
- 提供公开的 `Tick(Fix64 deltaTime)` 方法，由逻辑帧调度器统一调用
- 投射物的表现层（旋转、模型渲染）由独立的表现层组件在渲染帧中根据逻辑位置插值
- 如果投射物需要 GameObject 表现，可用一个轻量的 `ProjectileView : MonoBehaviour` 只负责渲染，逻辑由 `ProjectileController` 管理

**影响范围**：`ProjectileController` 需要重构为纯逻辑类，`ProjectileEffectSpec` 中的实例化逻辑需要调整。

---

### 2.5 Transform 直接操作 → 逻辑层位置管理

**原因**：`Transform.position` 是 Unity 引擎对象，直接在逻辑层操作会导致逻辑状态与引擎表现耦合。帧同步中逻辑层应维护纯数据的位置信息，表现层负责同步到 Transform。

**涉及文件与代码**：

| 文件 | 问题代码 | 说明 |
|------|---------|------|
| `Runtime/Effect/DisplaceEffectSpec.cs` | `_targetTransform.position = currentPos + _displaceDirection * moveStep` | 直接修改 Transform 位置 |
| `Runtime/Effect/DisplaceEffectSpec.cs` | `_targetTransform = target.Owner.transform` | 持有引擎对象引用 |
| `Runtime/Effect/ProjectileController.cs` | `transform.position = _currentPosition` | 直接修改 Transform |
| `Runtime/Effect/ProjectileController.cs` | `transform.rotation = Quaternion.Euler(...)` | 直接修改旋转 |

**改造方案**：

- 定义逻辑层位置组件（如 `LogicTransform`），包含 `FixVector3 Position`、`FixVector3 Rotation` 等纯数据字段
- 所有位移逻辑（`DisplaceEffectSpec`、`ProjectileController`）改为操作 `LogicTransform`
- 表现层组件（`ViewSync`）在渲染帧中读取 `LogicTransform` 并同步到 `UnityEngine.Transform`，可加插值平滑

**影响范围**：`DisplaceEffectSpec`、`ProjectileController`，以及需要新增 `LogicTransform` / `ViewSync` 体系。`Unit.cs` / `AbilitySystemComponent` 需要持有 `LogicTransform`。

---

### 2.6 动画系统耦合 → 逻辑动画分离

**原因**：当前技能的时间效果触发依赖动画播放时间（`_currentPlayTime`），而动画由 `AnimationComponent`（Unity Animator/Timeline）驱动。Animator 播放帧率不确定，且动画事件时机不可控。

**涉及文件与代码**：

| 文件 | 问题代码 | 说明 |
|------|---------|------|
| `Runtime/Ability/GameplayAbilitySpec.cs` | `PlayAnimation(_animationName, _isAnimationLooping)` | 调用引擎动画系统 |
| `Runtime/Ability/GameplayAbilitySpec.cs` | `_currentPlayTime += deltaTime` → `CheckTimeEffectTriggers()` | 时间效果触发依赖动画播放时间 |
| `Runtime/Ability/GameplayAbilitySpec.cs` | `SkillConstants.FramesToSeconds(durationFrames)` | 帧转秒 |
| `Demo/Battle/AnimationComponent.cs` | 封装了 Animator 调用 | 动画播放由引擎驱动 |

**改造方案**：

- 逻辑层维护一个"逻辑动画状态机"：记录当前播放的动画、已播放帧数、循环标志
- 时间效果触发改为基于逻辑帧计数（`LogicFrame`）判断，而非引擎动画时间
- 表现层 AnimationComponent 仍然播放真实动画，但只做视觉表现，不驱动逻辑
- 如果动画时长需要精确控制，可在逻辑层用帧数表示时长，表现层按帧播放

**影响范围**：`GameplayAbilitySpec` 中的动画相关逻辑，需要新增逻辑动画状态机。

## 3. 次要问题（建议改造）

### 3.1 Guid 非确定性

| 文件 | 问题代码 |
|------|---------|
| `Runtime/Core/AbilitySystemComponent.cs` | `Id = Guid.NewGuid().ToString()` |
| `Runtime/Ability/GameplayAbilitySpec.cs` | `SpecId = Guid.NewGuid().ToString()` |
| `Runtime/Effect/GameplayEffectSpec.cs` | `SpecId = Guid.NewGuid().ToString()` |

**原因**：`Guid.NewGuid()` 使用系统随机源/MAC地址，不同客户端生成的 ID 不同。  
**影响**：不影响战斗逻辑结果，但影响序列化、调试对比、对象引用。  
**方案**：改为使用确定性 ID 生成器（递增整数计数器，由逻辑帧调度器分配）。

### 3.2 集合遍历顺序

| 文件 | 问题代码 |
|------|---------|
| `Runtime/Core/SkillDataCenter.cs` | `Dictionary<string, SkillGraphData> _skillGraphs` 等多个 Dictionary |
| `Runtime/Effect/ProjectileController.cs` | `HashSet<AbilitySystemComponent> _hitTargets` |

**原因**：`Dictionary` / `HashSet` 的遍历顺序在不同运行环境下可能不同。  
**影响**：如果遍历结果参与逻辑判断（如目标搜索、命中去重），可能导致执行顺序不一致。  
**方案**：关键逻辑路径中的集合遍历改为 `List` 或排序后遍历；目标搜索结果按单位 ID 排序。

### 3.3 GameObject.Instantiate

| 文件 | 问题代码 |
|------|---------|
| `Runtime/Effect/ProjectileEffectSpec.cs` | `Object.Instantiate(nodeData.projectilePrefab, ...)` |

**原因**：`Instantiate` 生成引擎对象，对象 ID 和引用不确定。  
**影响**：不影响逻辑结果，但投射物管理需要确定性。  
**方案**：逻辑层用对象池管理投射物，用确定性 ID 标识，`Instantiate` 只在表现层执行。

## 4. 架构优势（已有的好基础）

以下设计使得改造可行而非推翻重写：

| 优势 | 代码证据 | 改造价值 |
|------|---------|---------|
| **Cue 节点与逻辑节点天然分离** | `SpecExecutor.GetNodeCategory()` 将 `ParticleCue`/`SoundCue`/`FloatingTextCue` 归为 `NodeCategory.Cue`，与 `Effect`/`Task`/`Condition` 分开 | 帧同步只需跳过 Cue 执行，表现层单独处理 |
| **deltaTime 由外部传入** | `AbilitySystemComponent.Tick(float)` → `Abilities.Tick(float)` → `EffectContainer.Tick(float)` → `GameplayEffectSpec.Tick(float)` → `GASTimer.Tick(float)` | 核心更新链不直接读引擎时间，替换时间源即可 |
| **标签系统天然确定性** | `GameplayTag` 本质是字符串比较，`HasTag` / `HasAllTags` / `HasAnyTags` 均为字符串匹配 | 无需改造，天然适合帧同步 |
| **数据驱动执行** | 技能 = `SkillGraphData`（ScriptableObject），`SpecExecutor` 解释执行节点图 | 数据本身确定性可保证，执行引擎可复用 |
| **节点执行顺序确定** | `SkillDataCenter` 缓存连接列表为 `List<ConnectionData>`，`SpecExecutor` 按列表顺序遍历 | 只要数据构建顺序确定，执行顺序就确定 |
| **效果生命周期管理完善** | `GameplayEffectSpec` 支持 Instant/Duration/Infinite、堆叠、刷新、过期策略 | 这些机制本身是纯逻辑的，替换数值类型后可直接复用 |

## 5. 改造路线图与优先级

```
Phase 1: 基础设施搭建
├── 1.1 引入定点数库（Fix64 / FixVector2 / FixVector3）
├── 1.2 搭建逻辑帧调度器（LockstepScheduler，固定帧率 Tick）
├── 1.3 定义 LogicTransform（纯数据位置/旋转）
└── 1.4 定义确定性 ID 生成器（递增整数）

Phase 2: 核心层改造
├── 2.1 AbilitySystemComponent.Tick 替换为 Fix64 deltaTime
├── 2.2 GASTimer / PeriodicTimer 替换为定点数
├── 2.3 GameplayEffectSpec 替换 Duration/Period/ElapsedTime 为 Fix64
├── 2.4 GameplayAbilitySpec 替换 ActivationTime / _currentPlayTime 为 Fix64
├── 2.5 移除所有 Time.time 引用，改用逻辑帧计数器
└── 2.6 移除所有 Guid.NewGuid()，改用确定性 ID

Phase 3: 效果层改造
├── 3.1 DamageEffectSpec：伤害计算改用定点数
├── 3.2 DisplaceEffectSpec：位移操作改为 LogicTransform，不再直接操作 Transform
├── 3.3 ProjectileController：去 MonoBehaviour 化，改为纯逻辑类 Tick
├── 3.4 ProjectileEffectSpec：实例化改为逻辑对象池
└── 3.5 其他 EffectSpec 子类逐一替换 float → Fix64

Phase 4: 目标搜索改造
├── 4.1 实现确定性空间分区（四叉树或均匀网格）
├── 4.2 TargetSearcher 改为遍历空间分区，用定点距离/角度判断
├── 4.3 搜索结果按确定性 ID 排序
└── 4.4 移除所有 Physics / Physics2D 调用

Phase 5: 动画与时间效果改造
├── 5.1 实现逻辑动画状态机（帧数驱动，非引擎动画时间）
├── 5.2 时间效果触发改为基于逻辑帧计数
└── 5.3 表现层 AnimationComponent 保持引擎动画播放，但只做视觉

Phase 6: 表现层分离
├── 6.1 Cue 节点执行推迟到渲染帧
├── 6.2 ViewSync 组件读取 LogicTransform 同步到引擎 Transform
├── 6.3 投射物表现层对象由对象池管理，跟随逻辑位置
└── 6.4 飘字/特效/音效在渲染帧中根据逻辑帧事件触发
```

## 6. 改造后的预期架构

```
逻辑层（确定性，固定帧率 Tick）
┌─────────────────────────────────────────────────┐
│  LockstepScheduler（固定步长 deltaTime = 1/30）   │
│                                                   │
│  AbilitySystemComponent                           │
│  ├── Abilities (Tick)                             │
│  │   └── GameplayAbilitySpec                     │
│  │       ├── 逻辑动画状态机（帧数驱动）             │
│  │       └── 时间效果触发（基于 LogicFrame）       │
│  ├── EffectContainer (Tick)                       │
│  │   └── GameplayEffectSpec                      │
│  │       ├── Fix64 Duration / Period / Elapsed   │
│  │       └── 逻辑层 Attribute 修改                 │
│  ├── OwnedTags（字符串比较，天然确定性）            │
│  └── LogicTransform（FixVector3 Position）        │
│                                                   │
│  TargetSearcher → 确定性空间分区查询                │
│  ProjectileController → 纯逻辑类 Tick             │
│  SpecExecutor → 跳过 Cue 节点                     │
└─────────────────────────────────────────────────┘
          │ 逻辑帧事件 / LogicTransform 状态
          ▼
表现层（渲染帧，非确定性，可插值平滑）
┌─────────────────────────────────────────────────┐
│  ViewSync → 读取 LogicTransform → UnityEngine.Transform │
│  CueExecutor → 特效/音效/飘字                      │
│  AnimationComponent → 引擎动画播放                  │
│  ProjectileView → 投射物渲染                       │
└─────────────────────────────────────────────────┘
```

> **总结**：框架的 GAS 架构（标签系统、数据驱动、节点图执行、Effect 生命周期管理）设计良好且可复用。主要改造工作量集中在 **定点数替换** 和 **物理/时间/驱动方式去引擎化** 三个方面。建议按 Phase 1→6 顺序逐步推进，每个 Phase 完成后可独立验证确定性。
